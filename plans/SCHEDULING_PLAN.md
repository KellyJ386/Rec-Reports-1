# Scheduling Module — Development Plan

## 1. Current state

- **DB schema exists** for the MVP core: `employees`, `certification_types`, `employee_certifications`, `schedule_periods`, `shift_templates`, `schedule_shifts`, `shift_assignments`, `schedule_publications` with RLS enabled and `schedule.read` / `schedule.manage` permission policies — `supabase/migrations/0003_scheduling.sql`, hardened (soft-delete filters, week-range check) in `supabase/migrations/0009_rls_hardening.sql`.
- **No schema exists** for `open_shift_claims`, `shift_swap_requests`, `time_off_requests`, or `employee_availability` (design doc §2.1); highest migration today is `0023_department_scope.sql`, so new work starts at `0024`.
- **Tested pure domain lib** — `src/lib/scheduling.mjs` (`shiftsOverlap`, `findDoubleBookings`, `findMissingCertifications`, `summarizeScheduleReadiness` with settings-registry config and per-cert enforcement via `effectiveEnforcementMode` from `src/lib/admin/cert-policy.mjs`); unit tests in `test/scheduling.test.mjs`.
- **Three end-user routes only** in `src/lib/http/scheduling-routes.mjs`: `GET /facilities/:id/schedule-periods`, `GET|POST /facilities/:id/shifts`, `POST /facilities/:id/schedule/validate`. No period CRUD, no template CRUD, no assignment endpoints, no PATCH/delete on shifts, no publish, no generate-from-templates, no employee self-service (`/me/schedule`), no approvals. Route tests with stubbed fetch in `test/scheduling-routes.test.mjs`.
- **Notable gap in the validate route**: it loads facility-wide shifts/assignments (not per-period), ignores `roleRequirements` (cert-policy per-requirement overrides), and passes no live config — so admin settings `scheduling.conflictCheckEnabled` / `scheduling.certEnforcementMode` are registered in `src/lib/settings-registry.mjs` (plus `publishCadenceDays`, `requireApprovalBeforePublish`, `openShiftClaimWindowHours`) but not actually read at request time.
- **UI is a read-only stub**: `src/public/index.html` panel `#schedule-list` ("Weekly coverage readiness") and `src/public/js/app.js` (~lines 199–265) render the first 5 shifts and a "Validate schedule" button calling `/schedule/validate`. No week grid, no template management, no assignment actions.
- **Established house patterns to copy**: injected-primitives route modules (`authenticate`/`sendJson`/`readBody`, `requireAuthPermission` from `src/lib/http/guard.mjs`), PostgREST helpers incl. `pgUpdate`/`pgDelete` in `src/lib/supabase-rest.mjs`, notification jobs (`buildNotificationJob` in `src/lib/admin/notifications.mjs`, tables in `0016_notifications.sql`), printable output via `src/lib/admin/pdf.mjs`, RLS SQL tests in `supabase/tests/` run by `scripts/run-rls-tests.mjs`.
- **Permission-code divergence**: implementation uses `schedule.read`/`schedule.manage`; the design doc (§11.2) specifies a finer-grained `scheduling.*` family (`.publish`, `.approve.swaps`, `.approve.time_off`, `.manage.open_shifts`, view scoping). A department-scope mechanism already exists (`0023_department_scope.sql`) but is not applied to scheduling reads.

## 4. Dependencies

- **Certifications/training module** — qualification gates already partially wired: `certification_types`/`employee_certifications` live in the scheduling migration itself; per-role requirement overrides come from `0017_cert_policy.sql` + `src/lib/admin/cert-policy.mjs` (`effectiveEnforcementMode`, `certGaps`). SC-06/SC-12/SC-19 depend on that module's `certification_role_requirements` rows and its route conventions (`src/lib/http/cert-policy-routes.mjs`). Training completions (`src/lib/training.mjs`) are a Phase-2+ input if training-based eligibility is added — keep the interface as "required codes per shift" so the source can widen without route changes.
- **Notifications** — SC-17 requires the `0016_notifications.sql` tables and `src/lib/admin/notifications.mjs` job/audience helpers plus `notification-routes.mjs` delivery; publish announcements and approval decisions are pure producers into that pipeline. No realtime broker exists yet; design §7 realtime is out of scope until a Supabase Realtime layer lands platform-wide.
- **Admin settings registry** — `src/lib/settings-registry.mjs` already registers the five scheduling keys; SC-06/SC-11/SC-21/SC-22 depend on `admin-config.mjs` for reading persisted per-facility values (`0008_admin_config.sql`), and any new key must pass `scripts/gen-settings-check.mjs`.
- **RBAC/permissions** — new permission codes (SC-07, SC-10, SC-20) must be seeded consistently with `0012_rbac_admin.sql` conventions and `has_permission` (note `0020` shadow fix); decide early whether to keep the implemented `schedule.*` prefix or migrate toward the design doc's `scheduling.*` codes — recommendation: keep `schedule.*` and amend the design doc, avoiding a permissions migration.
